# PRD：深度学习交互式学习网站 Deep Module 架构深化

## Problem Statement

当前项目已经从“能跑的教学脚本集合”升级成了一个面向初学者的深度学习交互式学习网站：静态主站、旧教材协议化、中央控制台、学习进度、八股文训练营、视觉系统和质量门都已经存在，并且自动检查可以通过。

真正的问题不再是功能缺失，而是核心工程能力正在集中到少数巨型入口里。主站壳层、质量门、中央控制台、视觉系统、课程目录事实、运行产物生命周期仍有明显的接口过宽问题。维护者如果想改一个路由、一个质量检查、一个训练联动图或一个产物解释，经常必须理解许多无关逻辑。

从用户视角看，这会带来三个风险：

- 学习产品继续迭代时，体验修复容易误伤旧脚本运行、质量门或中央控制台。
- 项目作为长期学习产品时，功能已经很丰富，但架构边界还不够清晰。
- 后续新增章节、动效、LayerNorm、残差块、多头注意力、训练遥测等能力时，会被巨型模块拖慢。

因此，下一阶段最值得做的事情是把项目的关键系统深化成一组稳定、可测试、低耦合的深模块。

## Solution

把下一阶段架构升级定义为“深模块化安全网工程”。优先顺序采用：

1. 质量门 Module 深化
2. 运行产物 Module 深化
3. 主站壳层 Module 深化
4. 中央控制台 Module 深化

随后再继续推进视觉系统、课程目录 Source of Truth、旧脚本协议 runtime 的统一。

这不是为了拆文件而拆文件，而是为了让每个模块封装大量复杂度，同时暴露少量稳定接口。最终效果应该是：

- 改首页体验时，不需要理解旧脚本运行。
- 改旧脚本产物解释时，不需要碰主站路由。
- 新增质量检查时，不需要编辑一个巨型检查脚本。
- 新增中央控制台组件时，不需要同时修改 shape 推导、代码生成、训练循环和页面 UI。
- 新增课程时，只改课程事实源，再由主站、知识图谱、质量门派生。

## User Stories

1. As a 维护者, I want 质量检查按领域拆分, so that 我新增一个检查时不需要读完整质量脚本。
2. As a 维护者, I want 每个质量检查模块有清晰失败信息, so that 我能快速判断是静态站、旧脚本、知识图谱还是视觉系统坏了。
3. As a 维护者, I want 质量门保留统一入口, so that CI 和本地命令不因为拆分而变复杂。
4. As a 维护者, I want 质量门模块只测试外部行为, so that 重构内部实现不会制造脆弱测试。
5. As a 维护者, I want 协议名单、重点路由和内容约束不散落在多个位置, so that 新增章节时不会漏改检查。
6. As a 维护者, I want 运行产物都有统一 run 生命周期, so that 旧脚本和新页面不会再污染根目录。
7. As a 学生, I want 旧脚本生成的图片能被主站解释, so that 我知道图是哪里来的、应该观察什么。
8. As a 维护者, I want stdout、stderr、status、图片、日志都挂在同一个 run 上, so that 调试失败脚本时证据完整。
9. As a 维护者, I want 根目录污染检查验证统一产物模块, so that 不是靠多处补丁互相兜底。
10. As a 维护者, I want 主站模块目录和路由逻辑独立, so that 我改课程入口不碰 Streamlit 兼容逻辑。
11. As a 维护者, I want 首页渲染和 CLI 启动解耦, so that 启动行为、页面 UI 和旧脚本运行可以分别测试。
12. As a 学生, I want 课程页路由稳定, so that 打开具体章节不会因为后台脚本变更而白屏。
13. As a 维护者, I want 静态站启动模块只关心端口、服务和路径, so that UI 变化不会影响启动逻辑。
14. As a 维护者, I want 旧脚本运行模块只关心协议、执行、产物和异常, so that 首页和 CLI 不需要知道脚本内部细节。
15. As a 维护者, I want 中央控制台的模型图核心逻辑独立, so that 新增层类型时可以先测图结构和 shape。
16. As a 维护者, I want shape 诊断独立, so that 非法连接能给稳定错误信息，而不是页面静默失败。
17. As a 维护者, I want 代码生成独立, so that PyTorch 输出可以用快照或行为测试验证。
18. As a 学生, I want 中央控制台训练联动更稳定, so that 调参数时损失、梯度、特征图和注意力热力图不会错位。
19. As a 维护者, I want 训练遥测独立, so that 教学模拟和真实训练可以明确区分。
20. As a 维护者, I want 中央控制台页面只消费核心模块结果, so that UI 可以继续打磨而不影响训练核心。
21. As a 设计维护者, I want 视觉系统分层, so that 改 tooltip、focus、reduced-motion 不会误伤具体学科动画。
22. As a 学生, I want 全站动效风格统一, so that CNN、RNN、Transformer、训练诊断看起来属于同一个学习产品。
23. As a 维护者, I want 设计 token 和具体动画解耦, so that 主题、间距、字体和运动偏好可以统一调整。
24. As a 维护者, I want 课程目录成为单一事实源, so that 主站、知识图谱、旧教材 manifest 和质量门不再重复维护课程名单。
25. As a 学生, I want 新增课程自动出现在目录、路径和知识图谱里, so that 学习路线不会断。
26. As a 维护者, I want 旧教材协议 runtime 统一, so that 新增教学页只需要写核心 compute 和少量 adapter。
27. As a 维护者, I want 手写旧脚本页面逐步收束到统一 lesson runtime, so that render、compute、smoke 的接口更小。
28. As a 维护者, I want 保留必要定制 adapter, so that 特殊教学页面仍能有独特交互而不破坏协议。
29. As a 项目维护者, I want 架构文档能解释这些深模块, so that 后续维护时能看出这是工程化项目，不只是页面集合。
30. As a 维护者, I want 每个阶段都能独立合并, so that 大重构不会一次性破坏整个学习站。

## Implementation Decisions

- 质量门优先拆分，因为它是后续架构调整的安全网。拆分后仍保留一个统一命令入口，内部委派到各领域检查模块。
- 质量门模块按领域组织：旧脚本协议、静态站体验、视觉系统、课程目录/知识图谱、学习进度、八股文训练营、运行产物、smoke。
- 运行产物模块优先收口 run 生命周期：创建 run、记录状态、捕获输出、保存图片、列出产物、生成教学解释上下文、清理或归档。
- 主站壳层拆分为：课程目录/路由、旧脚本执行与产物解释、首页/迁移提示渲染、CLI/静态站启动。
- 中央控制台拆分为：模型图核心、shape 诊断、代码生成、训练遥测、页面 adapter。
- 视觉系统拆分为：设计 token、基础教学 UI、通用 motion shell、具体学科动效、motion gallery。
- 课程目录事实源要能派生主站模块列表、知识图谱节点、旧教材映射、质量门重点路由和学习路径。
- 旧脚本协议继续统一到 lesson runtime 模式，保留特殊页面 adapter，但调用者不应该需要知道两套页面写法。
- 所有拆分都必须保持现有用户可见入口稳定：静态站 URL、课程 hash 路由、质量检查命令、旧脚本 smoke 行为不应破坏。
- 每次拆分应采用小步迁移：先引入模块和测试，再把原入口委派给新模块，最后删掉重复逻辑。
- 深模块接口应以稳定数据结构返回结果，而不是直接依赖页面框架对象。
- 运行产物、课程目录、质量门这些安全网模块优先于主站和中央控制台大拆分。

## Testing Decisions

- 测试只验证外部行为，不验证内部拆文件方式。目标是允许重构继续发生。
- 质量门模块测试应覆盖：检查通过时的汇总输出、检查失败时的领域化错误信息、统一入口是否仍执行全部检查。
- 运行产物模块测试应覆盖：run 创建、stdout/stderr/status 写入、图片登记、产物列出、根目录不污染、失败 run 可解释。
- 主站壳层测试应覆盖：模块目录派生、hash 路由解析、静态站启动端口选择、旧 Streamlit 迁移提示。
- 中央控制台测试应覆盖：合法模型图 shape 推导、非法连接诊断、代码生成输出、训练遥测事件结构、页面 adapter 消费结果。
- 视觉系统测试应覆盖：reduced-motion、focus-visible、tooltip、图表说明块、通用 shell 输出结构，不测试每个 CSS 像素。
- 课程目录事实源测试应覆盖：新增课程后能派生主站目录、知识图谱节点、重点路由、旧教材映射检查。
- 旧脚本 runtime 测试应覆盖：协议元数据、compute/render/smoke 合约、特殊 adapter 仍能接入统一 runtime。
- 继续保留全量质量检查作为集成回归测试；新增深模块测试作为更快、更局部的单元/组件测试。
- 现有严格旧脚本 smoke、重点页面 smoke、根目录污染检查、静态站检查都是可复用的测试先例。

## Out of Scope

- 不在本 PRD 中重写所有课程内容。
- 不在本 PRD 中更换前端技术栈。
- 不在本 PRD 中改变公开 URL、课程 hash 路由或启动命令。
- 不在本 PRD 中一次性重写中央控制台 UI。
- 不在本 PRD 中新增大量新课程、新动效或新模型层；这些应在深模块边界稳定后继续做。
- 不在本 PRD 中删除旧脚本兼容能力；旧脚本仍作为教学源码与 smoke 对象保留。

## Further Notes

这份 PRD 的核心判断是：项目现在最缺的不是更多功能，而是让已有功能的复杂度被更深的模块吞掉。

推荐执行顺序保持为：

1. 质量门 Module 深化
2. 运行产物 Module 深化
3. 主站壳层 Module 深化
4. 中央控制台 Module 深化
5. 视觉系统 Module 深化
6. 课程目录 Source of Truth 深化
7. 旧脚本协议 runtime 继续统一

其中前两项是后续大改的安全网，应该先做。安全网足够深之后，再拆主站壳层和中央控制台，风险会低很多。
